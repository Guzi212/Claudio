# Claudio 路线图

> 最近更新：2026-11-23（loic 拍板定位，见 [ADR-0001](adr/0001-product-positioning.md)）
>
> 这份文档管方向和优先级；具体技术任务记在 [`dev-plan.md`](dev-plan.md)。

## 定位

**给 AI Agent 用的本地音乐播放器。** Agent 负责选歌和主持，Claudio 负责找歌、出声、显示。

- 目标用户：普通用户（不会开终端、不会改 `.env`）
- 不做：Claudio 自己当大脑选歌（internal 冻结，阶段 1 存档移除）；只给元数据、拿不到直链的平台（Apple Music / Spotify 等，理由见 dev-plan 阶段二）

## 现状差距（2026-11-23 盘点）

| 差距 | 现状 | 对用户的影响 |
| --- | --- | --- |
| 没有需求入口 | GitHub 0 个 issue，反馈散在仓库外 | 不知道用户真正卡在哪 |
| 安装门槛高 | 要同级克隆 KuGouMusicApi、NeteaseCloudMusicApiEnhanced、QQMusicApi + Python venv，占 3 个端口，Node ≥ 22.12 | 普通用户基本装不上 |
| Agent 接入靠粘贴指令 | README 一段 prompt 发给 Grok Bot | 普通用户手里没有 Agent |
| 接口无版本 | README 点歌指令就是事实上的公开契约 | 改一次就打断别人的 bot |
| 两套大脑 | internal 选歌链路约 2700 行默认不跑 | 维护成本高，定位说不清 |
| 前端巨石 | `pwa/views/player.js` 2075 行、`styles.css` 1685 行、3 套主题 | 改一处动全身 |
| 从未发版 | 版本一直 0.1.0，没有给用户看的更新日志 | 用户不知道该不该更新、更新了什么 |
| 个人痕迹 | `state.db` 在仓库根；天气默认长沙；`user/` 品味语料 | 别人装上后行为奇怪 |
| 合规 | 三个音源都是非官方接口 | 扩散后风险随用户数放大 |

## 待定决策（未拍板前不动对应工作）

| # | 问题 | 选项 | 推荐 |
| --- | --- | --- | --- |
| D1 | 普通用户的 Agent 从哪来 | a 内置轻量默认主持（与 ADR-0001「不做大脑」冲突，需重开 ADR）<br>b 对接普通人已在用的聊天 bot，扫码配对<br>c 先不管，第一批用户由熟人帮忙配好 Agent | **c 过渡 → b 目标**：c 零成本，先验证有没有人真用；b 不违背定位 |
| D2 | 音源服务怎么到用户机器上 | a 安装包内置上游服务<br>b 安装器首次运行时从上游官方仓库拉取<br>c 保持手动 | **b**：仓库和安装包不分发非官方接口代码，用户体验接近 a |
| D3 | 分发形态 | a Electron 安装包（`desktop/` 已有壳）<br>b PWA + 后台服务安装器 | **a**：已有壳，托盘/开机自启/单点播放都已在桌面端做过 |

## 阶段

### 阶段 0：需求入口与地基（现在）

- [x] GitHub issue 模板：bug / 想要的功能 / 我怎么用它（本 PR）
- [ ] PWA 设置页加「反馈」入口，直达新建 issue
- [ ] 找 5 个说喜欢 Claudio 的人，各问三个问题：在什么场景打开它？哪一步最麻烦？没有它会用什么替代？
      结论去掉个人信息后记成 `user-feedback` issue，原始访谈不进仓库
- [ ] 旁观 1 个人从零安装，逐步记录卡点
- [ ] 打 `v0.1.0` tag，新建 `CHANGELOG.md`（用户能看懂的话）

### 阶段 1：收敛（清理 + 重构）

清理：
- [ ] internal 大脑打存档 tag `archive/internal-brain` 后从主干移除；常驻主持人单独评估
- [ ] 主题收敛到 1～2 套
- [ ] `state.db` 移到用户数据目录；默认值不再带任何个人配置（天气城市等）
- [ ] 核对并清理已合并分支的 worktree（2026-11-23 共 16 个，多数对应已合并 PR）
- [ ] `docs/handoffs/latest.md` 更新为当前状态

重构：
- [ ] 对外接口加 `/api/v1` 前缀 + 契约测试，保证 README 点歌指令永远能跑通
- [ ] `player.js` 按播放控制 / 歌词 / 队列 / leader 拆分
- [ ] 音源适配层（dev-plan 阶段二），点歌回落顺序可配置

### 阶段 2：普通用户装得上（依赖 D2、D3）

- [ ] 安装包 + 首次运行向导：拉取音源服务 → 扫码登录 → 配对 Agent → 试播一首
- [ ] 健康检查做成用户看得懂的自检页（哪个源掉了、点哪里修）
- [ ] 自动更新

### 阶段 3：按反馈迭代

只做有 issue 支撑的功能。现有候选：多音源阶段二（酷我/咪咕、B 站、YouTube Music）。

## 衡量

- 新用户从下载到出声 ≤ 10 分钟，全程不开终端（阶段 2 目标）
- 每月有效反馈 issue 数
- 音源掉登录后，用户能在界面里一键恢复
