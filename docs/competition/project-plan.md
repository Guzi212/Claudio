# Claudio · AI 私人电台项目计划书

## 一、项目背景与问题陈述

音乐已经成为学生和职场人进入学习、工作、通勤、休息状态的重要媒介，但真实使用中存在一个高频痛点：用户并不总是知道此刻该听什么。主流音乐平台拥有庞大的曲库和推荐流，却通常要求用户主动打开页面、浏览歌单、判断氛围、切换歌曲。对处在写作、复习、编程或通勤状态中的用户来说，这个过程会打断注意力，也会带来“选择太多反而无法决定”的负担。尤其当用户只是想快速获得一组适合当前情境的歌曲时，传统榜单、热门歌单和黑盒算法往往只能回答“大家在听什么”，很难回答“我现在适合听什么”。

Claudio 的出发点正是把音乐推荐从“内容浏览”转向“场景响应”。项目假设用户愿意提供少量个人化语料，例如喜欢的歌手、常听曲风、场景偏好、雷区和日常节奏；系统则利用这些语料，结合当前时间、最近播放历史以及可选的实时天气信息，主动生成一轮更贴近当下状态的播放建议。它不是替代大型音乐平台的完整曲库产品，而是围绕个人电台体验做轻量聚合：当用户输入“早安”“来点雨天聆听的”“今天好困”等自然语言时，Claudio 能像熟悉用户口味的 DJ 一样，给出简短说明和可直接播放的歌曲队列，从而减少选歌成本，帮助用户更快进入目标状态。

## 二、解决方案概述

Claudio 的解决方案可以概括为“AI 决策 + 音乐检索 + PWA 播放”的闭环。用户在浏览器中的 PWA 界面与 Claudio 对话，后端将用户输入交给路由层判断：以斜杠开头的命令会作为播放控制处理，普通自然语言则进入 AI 推荐链路。系统会构建包含角色约束、用户口味语料、日常节奏、当前时间、天气、最近播放和最近对话的 system prompt，让模型只输出符合 DJ schema 的 JSON 对象。JSON 中包含给用户看的简短话术、推荐曲目列表、推荐理由和串场词，后端再把曲目逐一交给酷狗音乐服务解析为可播放 URL。

这一设计的重点不是做一个“更复杂的播放器”，而是把用户最费心的环节前置交给 AI：理解语境、挑选氛围、控制曲目数量、说明推荐依据。前端负责把结果变成稳定的播放体验，包括队列展示、当前播放信息、进度条、音量、上一首/下一首、暂停、循环模式、收藏状态、歌词面板、天气展示和 Studio 主题切换。后端维护当前队列、播放索引、最近对话和播放历史，使刷新页面或重启服务后仍能保留关键上下文。整体方案保持本地可部署，依赖明确，适合个人用户快速试用，也为后续云端化和更多场景接入留出空间。

## 三、技术架构与实现

项目采用分层架构，核心链路为 `router → context → claude → state.db → services/kugou`。前端位于 `pwa/` 目录，使用原生 JavaScript 实现 Progressive Web App，无额外前端框架；后端位于 `server/` 目录，基于 Node.js、Express 风格 API 和 WebSocket 提供服务。`server/app.js` 挂载静态 PWA、聊天接口、播放状态接口、音频代理、歌词、天气、设置、健康检查和 Studio 状态接口；同时维护内存中的运行时队列，并通过 WebSocket 将状态推送到在线客户端。音频代理 `/api/proxy` 会转发酷狗直链并支持 Range 请求，降低浏览器端直接播放外部链接时遇到的防盗链和拖动进度问题。

AI 层由 `server/claude.js` 封装。当前实现支持在配置 DeepSeek API key 时直接调用 DeepSeek 聊天接口；未配置时回退到 `claude -p --output-format json` CLI。无论底层模型来源如何，代码都会先解析 CLI 或 API 外层响应，再解析项目定义的 DJ JSON。若模型输出夹带说明文字，解析函数会尝试抽取第一个 JSON 块；若仍失败，则把原文作为 `say` 并返回空播放列表。若模型调用超时或失败，系统会从 SQLite 中最近播放记录取出若干首作为兜底推荐，保证用户不会因为单次模型异常完全中断体验。

上下文层由 `server/context.js` 负责。它读取 `prompts/dj-persona.md` 中的角色与 schema 约束，读取 `user/taste.md` 和 `user/routines.md` 中的用户语料，加入当前时间分桶、OpenWeather 天气结果、可选的飞书日历当日事件，以及 SQLite 中的最近播放和最近对话。数据库使用 Node 22.5+ 内置 `node:sqlite` 的 `DatabaseSync`，自动创建 `messages`、`plays`、`prefs`、`unmatched` 等表，分别保存对话、播放历史、设置和未匹配歌曲。音乐服务位于 `server/services/kugou.js`，负责调用本地部署的 KuGouMusicApi 搜索、打分、获取播放直链和歌词，并把无法匹配的曲目写入 `unmatched`，便于后续优化口味语料和搜索策略。

## 四、核心功能与亮点

项目已经具备一条完整的 AI 推歌到播放闭环。用户输入自然语言后，Claudio 会依据个人口味、当前时间、历史播放和环境信息生成 1-5 首歌曲，而不是简单返回热门歌单。`prompts/dj-persona.md` 对模型输出有严格约束：必须只返回 JSON，默认推荐 3-5 首，明确指定单曲时只返回 1 首，同一轮不连续推荐过多同一艺人，并以 `taste.md` 为最高优先级但尊重用户当下输入。这使推荐结果既有个性化，又能被后端稳定解析和执行。

播放器体验是第二个亮点。PWA 端不仅显示聊天气泡和推荐理由，还会把可解析曲目变成当前播放队列，支持播放、暂停、上一首、下一首、进度拖动、音量调整、列表循环与单曲循环。前端会把真实播放索引同步回服务端，避免浏览器与后端状态漂移；启动时也会拉取 `/api/now` 和 `/api/studio/state` 恢复上次会话。歌词面板、天气组件和 Studio 主题进一步强化“私人电台”的感受：用户看到的不只是一个搜索框，而是一个围绕当下歌曲、天气、时钟、队列和电台状态组织起来的操作界面。

第三个亮点是透明和可扩展。与黑盒推荐流相比，Claudio 会把推荐理由以简短文字返回，用户能理解本轮歌曲为何被选中。偏好数据不是隐藏在平台算法中，而是放在本地 `user/taste.md`，用户可以直接编辑；酷狗 OCR 文本、分享链接或歌单文本也可通过导入脚本蒸馏为口味摘要。系统还支持可选的 Fish Audio TTS，把 AI 的 `say` 合成为串场音频放入队列；若未配置密钥则自动跳过，不影响歌曲播放。天气、日历、调度器和设置接口均以模块化方式挂载，使后续扩展不会破坏核心推荐链路。

## 五、用户价值与体验

Claudio 面向的核心用户是学习、工作和通勤场景中的个人音乐使用者。对学生而言，复习、写论文、做项目时最重要的是尽快进入专注状态，而不是在多个歌单之间反复比较。Claudio 可以根据上午、午间、夜里等时间分桶，结合用户的日常节奏和历史播放，给出更贴合状态的音乐队列。对职场人或开发者而言，工作间隙的一次音乐选择也可能造成注意力切换成本；通过一句自然语言让系统直接安排一轮播放，能减少打开平台、搜索、筛选、试错的时间。

从体验上看，Claudio 的交互更接近“对一个懂自己口味的 DJ 说话”。用户不需要学习复杂参数，可以输入“早安”“来点不吵的”“今天好困”“放周杰伦的晴天”等自然表达。系统会在短句中回应，并把推荐理由和歌曲队列展示出来。推荐结果失败时也有降级路径：模型异常时可从历史播放兜底，歌曲匹配失败会记录在数据库中，酷狗搜索失败会在前端提示用户检查上游服务。这样的设计使用户既能感到 AI 的主动性，又不会因为外部服务波动而失去基本可用性。

本地部署也是当前阶段的重要价值。用户的口味文件、播放历史、偏好设置和对话记录保存在本机，适合对个性化和隐私有要求的个人使用。项目没有把体验绑定到某个封闭平台，而是用可读 Markdown、SQLite 和明确的环境变量组织数据。用户可以逐步增加自己的偏好语料，也可以检查 `unmatched` 表了解哪些推荐没有找到可播放版本。这种可解释、可修正、可迁移的方式，让 Claudio 不只是一次性推荐工具，而是可以随使用者成长的个人音乐助理。

## 六、项目进展与规划

当前项目已经完成 MVP 的主要工程闭环：本地 Node 服务可以启动 PWA，用户输入自然语言后进入 AI 推荐链路，推荐结果会被解析为酷狗可播放队列，前端能够进行基础播放控制和状态展示。SQLite 已用于保存消息、播放历史、偏好和未匹配歌曲；KuGouMusicApi 上游服务负责搜索、直链和歌词；OpenWeather 可为上下文和前端组件提供天气数据；设置接口支持运行期读取部分密钥和配置。测试方面，项目使用 Vitest，`package.json` 中提供 `npm test`，同时 README 给出了端到端验证清单，覆盖启动、聊天推荐、自动播放、切歌、暂停、进度条和状态恢复等关键路径。

短期规划首先是打磨稳定性和参赛展示体验。包括补充更聚焦的测试用例，覆盖 DJ JSON 解析、酷狗匹配打分、上下文拼装、调度任务和前端状态同步；完善 README 与实际代码的一致性，让可选 DeepSeek、Claude CLI、Fish Audio、OpenWeather、飞书日历等能力的配置边界更清楚；优化未匹配歌曲的反馈方式，使用户更容易修正 `taste.md` 或搜索提示。对于竞赛演示场景，还可以准备一组示例口味文件和固定测试 prompt，保证评委能在短时间内看到“输入场景语句 → 生成推荐理由 → 形成可播放队列”的完整流程。

中长期规划则围绕三条方向展开。第一是云端化与多端访问，在保持本地隐私选项的同时，提供更容易部署的 Web 服务版本。第二是更细的场景感知，例如把日历、专注时段、通勤状态和天气预报作为可配置输入，但只在用户授权和明确配置后启用。第三是推荐质量迭代，通过播放反馈、收藏状态、跳过行为和未匹配记录持续修正口味画像。项目不会追求一次性做成大而全的音乐平台，而会保持“个人 AI 电台”的定位，把推荐速度、解释性和当下场景适配作为核心指标。

## 七、总结与展望

Claudio 的核心意义在于把 AI 能力落到一个具体、常见且可感知的日常问题上：当用户想听音乐但不想花时间选择时，系统能否理解他的口味和当下状态，并直接给出一组可以播放的答案。现有实现已经证明这条路径可行：模型负责理解和决策，结构化 JSON 让结果可执行，酷狗服务提供曲库检索和播放来源，PWA 承担稳定的交互和音频播放，SQLite 保留长期上下文。各模块职责清晰，失败时有兜底，扩展时也有明确边界。

从竞赛角度看，Claudio 的价值不在于堆叠大量概念，而在于完成了一个能够实际运行的 AI+效率工具原型。它把“减少选择成本、帮助进入状态、尊重个人偏好”作为产品目标，把“可对话、可解释、可播放、可本地部署”作为工程落点。未来，随着推荐反馈、调度提醒、语音串场和更多授权环境数据逐步完善，Claudio 可以从一个本地个人电台成长为更完整的生活节律助手：它不仅知道用户喜欢什么歌，也能在合适的时间，用合适的声音，帮助用户切换到更适合当前任务的状态。
